Findings

1. L1↔L2 is equal on both (≈56 GB/s) — already at the PCIe Gen5 ×16 ceiling.
2. B200 transfer kernels are 1.4–1.85× faster than MI355X (newer CUDA kernels vs the 9-month-stale AMD AOT kernel); B200 also has no backup pf-penalty (lf 30.4 = pf 30.4), while MI355X drops 22.4→19.6.
3. The NVMe drives are NOT slow — earlier "1 GB/s" was a benchmark artifact. True O_DIRECT 288 MB single-stream (same harness): MI355X /data (1 drive) write 5.7 / read 6.0; B200 /raid write 29.3 / read 18.8. B200's /raid is a striped multi-NVMe array — ~5× the MI355X single drive. The old Python harness over-stated reads (page-cache leak) and under-stated writes (tobytes() copy, no O_DIRECT).
4. pf→lf LOAD penalty on both (~2.7–2.85× vs lf→lf): MI355X 5.4 vs 15.4, B200 10.0 vs 27.2. Fixed by the JIT kernel (see 6).
5. The L2→L3 backup bottleneck is software, not hardware — and it's the buffered single-stream write, not fsync. The file backend's set() just does numpy.tofile() (buffered, no fsync), giving only ~1.5–1.6 GB/s on both boxes. fsync is nearly free here (buffered no-fsync 1.76 vs +fsync 1.64); the gap to the drive is the buffered page-cache path itself (memcpy + dirty-page writeback throttling + low queue depth). O_DIRECT large-block hits 5.7 (MI) / 29.3 (B200), so the drive is almost idle: ~3.5× headroom on MI355X, ~20× on B200. Fix = O_DIRECT / parallel writers, not removing fsync.
6. JIT kernel (PR #25154) fixes the MI355X transfer gap. On MI355X the JIT (non-temporal, unrolled) kernel beats the AOT kernel 2.0–3.7×, and on the two production paths it more than doubles them: load pf→lf 5.4→12.1 (now > B200 AOT 10.0), backup lf→pf 19.6→39.6 (now > B200 AOT 30.4).
Net: L1↔L2 is at the PCIe ceiling on both. NVMe hardware is fast (MI 6, B200 19–29 GB/s); the real L2↔L3 bottleneck is HiCache's buffered single-stream tofile() write (~1.5 GB/s, no fsync involved), which wastes most of the drive — fixable in software (O_DIRECT / parallel writers), with the biggest win on B200. On GPU transfer, AOT favors B200, but PR #25154's JIT kernel brings MI355X to/above B200 AOT.

Host → Device data path — where the bottleneck is

A host→device copy (HiCache L2→L1) crosses two different buses in series: the CPU memory channel (DRAM→CPU) and the PCIe link (CPU→GPU). Throughput is capped by the slower one — for L1↔L2 that is PCIe (~56 GB/s), not DRAM (~563 GB/s on the B200 host). This is why Findings #1's L1↔L2 ≈56 GB/s sits at the PCIe Gen5 ×16 ceiling.
pinned vs pageable: HiCache L2 is allocated pinned via cudaHostRegister (see memory_pool_host.py:alloc_with_host_register; ROCm hits the same default path, key "cuda"), so the DMA engine reads host RAM directly — no intermediate staging copy. A pageable buffer would force the driver to first memcpy into a pinned staging area (an extra DRAM round-trip), roughly halving effective throughput.
Single vs concurrent: one GPU pulls ~56 GB/s — far under DRAM's 563 GB/s, so PCIe is the cap. Under TP8 (DeepSeek-R1 MLA replicates KV on every GPU) all 8 GPUs transfer at once; GPUs split 4-per-socket, so each socket sees 4 × 56 ≈ 224 GB/s vs ~281 GB/s/socket DRAM — DRAM then becomes co-limiting (only ~25% headroom) if buffers are NUMA-local; mis-binding sends traffic over the inter-socket link and makes it worse.

Per-socket concurrency — GPUs do NOT share one PCIe link

Common misconception: 4 GPUs on a socket queue for one 56 GB/s pipe. Wrong. Each GPU has its own dedicated PCIe Gen5 ×16 link (~56 GB/s each, verified: all 8 B200 at gen5/×16). They run in parallel — no queueing at PCIe. The shared resource they do contend for is the socket's DRAM (one memory controller feeding all 4 local GPUs + the CPU).

Note — transfer direction vs name vs method

Tiers: L1 = GPU HBM, L2 = host pinned RAM, L3 = NVMe / storage backend.
directionoperation namemethod / objectwhen
L2→L1 (host→device, load back to HBM)load (load-back)load(), load_buffer, LayerLoadingEventon prefix hit whose data sits in host; loaded synchronously at schedule time
L1→L2 (device→host, back up to host)write-to-host (backup-to-host)write(), write_buffer, write_backup()governed by --hicache-write-policy (see below)
L3→L2 (storage→host)prefetchprefetch_thread, PrefetchOperationasync; --hicache-storage-prefetch-policy decides whether to wait
L2→L3 (host→storage)backup (write to storage)write_storage(), backup_thread_funcafter a host hit / backup, persisted to storage
write_back is a policy, not a direction name. It is one value of --hicache-write-policy controlling when the L1→L2 write-to-host happens:
  • write_through — write on hit (threshold=1, almost immediately) → host is a superset of device (inclusive).
  • write_back — write only when the device entry is evicted.
  • write_through_selective — write after hit count reaches a threshold (=2).
The best_effort / wait_complete / timeout prefetch policy applies only to L3→L2; L1/L2 hits are synchronous.
Capacity (under write_through): since L2 (host) is a superset of L1 (device), the effective cache size ≈ L2 alone — not L1+L2. L1 is just the HBM-resident subset.

0609 — E2E JIT enablement & GPU-bubble analysis (DeepSeek-R1 FP8, 30 clients, L1 10 / L2 20)

1. JIT HiCache kernel was never actually used in any FP8 run — both platforms ran AOT.
  • MI355X (ROCm): blocked by memory_pool_host: can_use_jit = _is_cuda and … — _is_cuda is False on ROCm.
  • B200 (CUDA): passes _is_cuda but blocked by can_use_hicache_jit_kernel(576)=False — FP8 MLA element = 576 B and the gate required %128==0 (576%128=64). JIT only engaged for BF16 KV (element 1152).
Confirmed by traces: both show only AOT transfer_kv_*_mla_* kernels, zero JIT.

2. Fix (committed): make JIT usable for FP8 576 on ROCm.
  • hicache.cuh load_vec: adaptive vector unit (16/8/4 B) instead of a fixed 128-B loop → supports any element that tiles across threads (576 = 9×64). No regression for 1152.
  • hicache.py gate %128 → %64; memory_pool_host JIT gate _is_cuda → (_is_cuda or _is_hip).
  • Validated: byte-exact round-trip, GSM8K 0.94–0.95 (correct), microbench load pf→lf 3.2→8.9 GB/s (2.8×), backup lf→pf 14.3→28.0 (2.0×). After the patch the E2E trace shows hicache_transfer_per_layer (JIT), no AOT.

4. What causes the MI355X bubbles — two distinct kinds (CPU is NOT the cause: EPYC 9575F 64-core ≥ B200 Xeon 8570):
  (a) transfer-gated — the 185–283 ms gaps. The scheduler/cache-controller host threads stall (lock/queue) while the slower AOT transfer + single-drive L3 work drains. Fixed by JIT (+RAID0): gaps drop to <30 ms.
  (b) request-arrival / scheduling — the big queue.get/wait gaps + the round barrier. The scheduler is idle waiting for the next batch of client requests; not transfer-related — JIT/RAID0 cannot help. Needs higher concurrency (max_parallel) and/or async/overlapped cache management.

Why FP8 idles more than BF16: the host-side coordination (a)+(b) costs a roughly fixed wall-time; FP8 attention shortens GPU compute so the GPU finishes early and exposes that wait as idle, whereas BF16's longer compute overlaps/hides it (≈0% idle). Both attentions give nearly the same round time (~17 s) — the round is gated by the host path, not by compute.

0609 net: JIT now works end-to-end on MI355X FP8 (was silently AOT) and removes the transfer-gated bubbles; the remaining idle is concurrency/scheduling-bound.

5. Higher concurrency fills the idle bubbles — but it is not automatically a win. Re-profiled JIT+RAID0+FP8 with max_parallel 8→64 and 100 clients (wait_complete):

At mp64/100c the GPU idle collapses 47%→12% (the request-arrival bubbles get filled — confirming they are concurrency-fixable), but the GPU is now busy doing wasted re-compute: 100 clients × growing prompts (R8 ≈ 3.6M tokens) overflow L2=20 GB (≈611K fp8 tokens), the cache thrashes, hit collapses to ~0.12, and TTFT explodes to 20–66 s. Filling bubbles ≠ faster when the cache cannot hold the working set.

Sweet spot for JIT/RAID0 to help TTFT: high concurrency and L2 large enough to hold the working set (≈120 GB+ for 100 clients here) so hit stays high and the time is spent on L3→L2→L1 transfer (which JIT/RAID0 accelerate) rather than re-compute. Neither mp8/30c (GPU idle, but high hit / low TTFT) nor mp64/100c-with-small-L2 (GPU busy, but thrashing) is that regime.
