Findings

1. L1↔L2 is equal on both (≈56 GB/s) — already at the PCIe Gen5 ×16 ceiling.
2. B200 transfer kernels are 1.4–1.85× faster than MI355X (newer CUDA kernels vs the 9-month-stale AMD AOT kernel); B200 also has no backup pf-penalty (lf 30.4 = pf 30.4), while MI355X drops 22.4→19.6.
3. The NVMe drives are NOT slow — earlier "1 GB/s" was a benchmark artifact. True O_DIRECT 288 MB single-stream (same harness): MI355X /data (1 drive) write 5.7 / read 6.0; B200 /raid write 29.3 / read 18.8. B200's /raid is a striped multi-NVMe array — ~5× the MI355X single drive. The old Python harness over-stated reads (page-cache leak) and under-stated writes (tobytes() copy, no O_DIRECT).
4. pf→lf LOAD penalty on both (~2.7–2.85× vs lf→lf): MI355X 5.4 vs 15.4, B200 10.0 vs 27.2. Fixed by the JIT kernel (see 6).
5. The L2→L3 backup bottleneck is software, not hardware — and it's the buffered single-stream write, not fsync. The file backend's set() just does numpy.tofile() (buffered, no fsync), giving only ~1.5–1.6 GB/s on both boxes. fsync is nearly free here (buffered no-fsync 1.76 vs +fsync 1.64); the gap to the drive is the buffered page-cache path itself (memcpy + dirty-page writeback throttling + low queue depth). O_DIRECT large-block hits 5.7 (MI) / 29.3 (B200), so the drive is almost idle: ~3.5× headroom on MI355X, ~20× on B200. Fix = O_DIRECT / parallel writers, not removing fsync.
6. JIT kernel (PR #25154) fixes the MI355X transfer gap. On MI355X the JIT (non-temporal, unrolled) kernel beats the AOT kernel 2.0–3.7×, and on the two production paths it more than doubles them: load pf→lf 5.4→12.1 (now > B200 AOT 10.0), backup lf→pf 19.6→39.6 (now > B200 AOT 30.4).
Net: L1↔L2 is at the PCIe ceiling on both. NVMe hardware is fast (MI 6, B200 19–29 GB/s); the real L2↔L3 bottleneck is HiCache's buffered single-stream tofile() write (~1.5 GB/s, no fsync involved), which wastes most of the drive — fixable in software (O_DIRECT / parallel writers), with the biggest win on B200. On GPU transfer, AOT favors B200, but PR #25154's JIT kernel brings MI355X to/above B200 AOT.

Note — transfer direction vs name vs method

Tiers: L1 = GPU HBM, L2 = host pinned RAM, L3 = NVMe / storage backend.
directionoperation namemethod / objectwhen
L2→L1 (host→device, load back to HBM)load (load-back)load(), load_buffer, LayerLoadingEventon prefix hit whose data sits in host; loaded synchronously at schedule time
L1→L2 (device→host, back up to host)write-to-host (backup-to-host)write(), write_buffer, write_backup()governed by --hicache-write-policy (see below)
L3→L2 (storage→host)prefetchprefetch_thread, PrefetchOperationasync; --hicache-storage-prefetch-policy decides whether to wait
L2→L3 (host→storage)backup (write to storage)write_storage(), backup_thread_funcafter a host hit / backup, persisted to storage
write_back is a policy, not a direction name. It is one value of --hicache-write-policy controlling when the L1→L2 write-to-host happens:
  • write_through — write on hit (threshold=1, almost immediately) → host is a superset of device (inclusive).
  • write_back — write only when the device entry is evicted.
  • write_through_selective — write after hit count reaches a threshold (=2).
The best_effort / wait_complete / timeout prefetch policy applies only to L3→L2; L1/L2 hits are synchronous.
Capacity (under write_through): since L2 (host) is a superset of L1 (device), the effective cache size ≈ L2 alone — not L1+L2. L1 is just the HBM-resident subset.
